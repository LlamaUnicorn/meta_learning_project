## Активные направления

### 1. Разобрать агентскую фичу из шести коммитов

**Статус:** самостоятельный черновик PR description уже написан и получил вопросы о точности; ответы и техническая проверка еще не задокументированы. **Не считать кейс завершенным.**

**Исходные данные:** пользователь работает над фичей из 6 коммитов с изменениями во многих файлах; ни полный diff, ни список затронутых компонентов в учебном репозитории пока не записаны. Не выдавать предположения о ее архитектуре за факты.

**Цель:** объяснить фичу без line-level memorization; аргументировать дизайн и границы; проверить понимание поведением.

**Один легкий проход:**
1. **Своими словами** набросать PR description и commit messages, не читая предварительно готовый текст агента. Описать поведение и границы; коммиты использовать как карту изменений, **не** читать все подряд.
2. Попросить вопросы **без переписывания текста**: кто действует, что именно меняется, когда и почему; как устроены статусы, retries, отказ и дубликаты.
3. По пробелам составить маршрут: вход → компоненты → данные / побочные эффекты → выход. Найти ответы в коде/тестах; пройти один реальный сценарий (при возможности debugger, UI или безопасный probe).
4. Изменить вход/условие, **предсказать результат до проверки**. Особое внимание — сохранению результатов после ответа 202, отсутствию ответа, неполной конфигурации и параллельной обработке; считать это вопросами, а не установленными фактами.
5. **Самостоятельно переписать PR**; устно объяснить один путь и 2 точки отказа; неизвестное отметить.

**Артефакт после выполнения:** 5–10 строк в журнале: карта / один путь / проверенные failure points / защищенные решения / что пока неизвестно / что улучшить в методе. Не плодить большой документ или чек-лист на каждый коммит.

## Идея для отдельного эксперимента: журнал препятствий агента (2026-10-19)

**Цель:** помочь агенту не повторять проектно-специфичные ошибки между сессиями. Это дополнение к существующим папкам с планами и находками по задачам, а не замена их памяти. Пока только предложение: `AGENTS.md` рабочего проекта не меняем.

**Предполагаемый механизм:**
1. В `AGENTS.md` — короткая ссылка на `gotchas.md`: если при выполнении задачи обнаружился неожиданный сбой или неочевидная особенность проекта, поискать там подходящий случай. Не загружать весь файл автоматически при старте каждой сессии.
2. Если готового решения нет, разобраться и проверить его. Записывать только неочевидные, специфичные для проекта и потенциально повторяющиеся препятствия. Несколько неудачных попыток сами по себе не повод делать запись.
3. Краткий формат записи: **симптом и операция → причина (или «не установлена») → проверенное решение и способ проверки → возможное устранение первопричины**. Отделять догадки от фактов, не сохранять секреты.
4. Агент может сам предложить или добавить запись. Человек периодически просматривает журнал, превращает системные проблемы в задачи, улучшает команды/настройки/документацию и удаляет устаревшие обходные пути.
5. Хранить записи короткими и доступными для точечного поиска; не превращать `gotchas.md` в огромную инструкцию.

**Проверка гипотезы:** за несколько рабочих сессий выяснить, замечает ли агент полезные исключения, находит ли решения при повторном сбое и сокращает ли повторные попытки. Отдельно оценить, обнаруживаются ли благодаря журналу неудобства самого проекта.
