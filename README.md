# Practice Experiment — статус

**Обновлено: 2026-10-19.** Это точка входа в проект. Статус ниже отражает только зафиксированные попытки и обсуждения; незаписанную работу не считаем выполненной.

## Зачем этот проект

Стать способным **самостоятельно понимать, объяснять, проверять, отлаживать и изменять код**, в том числе сгенерированный AI-агентом. Не требуется помнить имена функций и каждую строку. Требуется понимать поведение, путь выполнения, существенные архитектурные решения и места возможного отказа.

Методы обучения здесь тоже являются предметом эксперимента: сравниваем, что действительно помогает, а не просто собираем советы.

## Две практики и одна общая методика

| Направление | Цель | Что делаем |
| --- | --- | --- |
| **1. Deliberate practice** | Развивать независимое рассуждение о коде | Короткие упражнения: понять входы → предсказать → проверить → объяснить расхождения → повторить позже. Сейчас основной материал — Python-код из реального проекта; первоначально пробовали и небольшие Go-фрагменты. |
| **2. Real-world comprehension** | Осмысленно владеть агентским кодом, который идет в реальную работу | По готовой функции/фиче составить карту, пройти сквозной сценарий, исследовать риски и альтернативы, проверить предсказания поведением. |
| **Meta-learning (сквозное)** | Проверять эффективность приемов | Записывать гипотезу о методе, наблюдение, ограничение и решение «оставить / изменить / пока неясно». |

Разработка фичи и наш четырехшаговый процесс доставки остаются отдельным рабочим процессом. Этот репозиторий фиксирует **обучение пониманию**, а не управляет разработкой.

## Сейчас в работе: пишу сам, чтобы понимать

**Новый рабочий прием (2026-10-19): писать собственные commit messages и PR description до того, как агент предложит готовый текст.** Это не экзамен по памяти: можно открывать исходники, но объяснение, термины и итоговая формулировка должны быть моими. Агент **задает точные вопросы и указывает пробелы**, а не пишет текст вместо меня.

**Короткий цикл прямо в IDE:**
1. **Сформулировать самостоятельно**, что изменилось для пользователя/системы (commit — один смысловой кусок; PR — сквозное поведение).
2. **Получить вопросы вместо переписывания**: какой именно объект, актор, триггер, статус, условие, порядок? Что при повторе, таймауте, частичном сбое, параллельном запуске?
3. **Вернуться к нужному месту кода и, если возможно, проверить прогноз** коротким реальным сценарием; не считать слова агента подтверждением.
4. **Переписать текст собственными словами** и явно отметить неизвестное. Можно закончить, когда объяснение конкретное и подтверждено настолько, насколько требует риск фичи.

Фокус: **не «эта штука делает то», а кто / что / когда / при каких условиях / с каким результатом / когда не работает / почему выбран такой способ**. Это практический вариант «защиты у доски», встроенный в нормальную работу и с быстрым результатом — текстом в IDE. См. [наблюдение и вопросы в findings.md](findings.md).

## Текущий принцип review

Для шести коммитов **не нужно перечитывать все изменения по порядку и заучивать реализацию**. Сначала разобраться в конечном поведении системы; история коммитов служит указателем на изменения, а не обязательным маршрутом чтения.

Минимальная «защита у доски» (критерий, а не новая обязательная бюрократия):

1. **Что происходит?** Показать один реальный сценарий от входа до результата.
2. **Почему так?** Объяснить ключевые решения и хотя бы одну альтернативу, не выдумывая мотивацию авторов.
3. **Где ломается?** Назвать вероятные ошибки, границы доверия и последствия некорректных входов/сбоев.
4. **Чем подтверждено?** Сделать предсказание, изменить условие и наблюдать результат (UI, безопасный локальный запуск, debugger, тест или probe).

Умение объяснить решение **не доказывает**, что решение корректно; нужны проверки. Для учебных упражнений из [plan.md](plan.md) продолжают действовать строгие ограничения на запуск: только разрешенные операции с объектами в памяти, без сервиса и инфраструктуры.
